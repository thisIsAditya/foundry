# Web frontend information architecture delta

**Implements:** `docs/02-product-requirements/02-web-requirements.md` (all sections).
**App:** `apps/web`. Extends the existing Next.js 16 App Router structure in `docs/plan/implementation/02-web-frontend-architecture.md`; no rendering-model change (RSC for reads via `lib/trpc/server.ts`, TanStack Query via `lib/trpc/client.ts`, SSE for streaming, Server Actions never carry shared mutations).

Final top-level project nav (`components/chrome/project-nav.tsx`, extended not replaced): **Overview, Co-founder, Business model, Work board, Research & evidence, Decisions, Settings** — exactly the 7 destinations in web requirements §1.

## 2. Overview screen

`home-dashboard.tsx`/`project-desk.tsx` are the closest existing analogs and are refactored in place, not rewritten from scratch — they already know how to fetch project-scoped data via tRPC and render cards. New composition, per web requirements §2, all above the fold:

- Venture name + one-sentence summary — new, generated once by `InitialDraftService` and re-generated by the co-founder when the problem/beachhead sections change materially.
- Overall score + dimension chips — `score.getCurrent`, rendered with a new `ScoreDimensionChip` component in `@foundry/ui` reusing the existing `StatusPill`/`Badge` primitives (no new design-token set).
- Known/assumed/missing summary — derived from `pack.listBusinessModelSections`' per-section status counts, no new query.
- Highest-impact finding — top `ScoreReason` from `score.getCurrent`.
- One recommended next action — top `ScoreImprovementAction`.
- Running AI work — `job.list(projectId, 'kanban')` filtered to `running`/`queued`.
- Founder tasks waiting — `founderTask.list(projectId, 'active')`.
- Revision waiting for review — `pack.listRevisions` filtered to `status: 'draft'`.
- Research plan waiting to start — `job.list` filtered to `jobKind: 'research', status: 'proposed'`.
- Provider/privacy mode + cost — `provider.listConnections` + `budget.getSummary`, both already implemented, just newly surfaced here instead of only in the provider panel.

## 3. Persistent co-founder panel

New component, `components/chrome/cofounder-panel.tsx`, mounted in `(app)/p/[projectId]/layout.tsx` (the existing project layout that already renders `ProjectNav`). Behavior required by web requirements §4: preserves scroll position and unread state across navigation — implemented as a single mounted instance (not remounted per route) using the existing per-project Zustand store pattern already used for `useSprintStream` (`lib/stream/use-project-stream.ts` is extended, not duplicated, to also carry conversation state). Collapses to icon-only below `lg`; the dedicated `/co-founder` route is what mobile-width and narrow desktop users land on instead of the panel (web requirements §12 responsive requirement).

Message rendering: a `ConversationMessageView` component switches on `ConversationBlock.kind` to render the 10 response-type variants (concise answer, cited finding, assumption card, proposed plan change, research plan, founder task, job creation request, draft action, decision card, blocker) as typed cards, each linking (via `ConversationReference`) into the Business model, Work board, or Decisions destinations — plain chat text alone is never sufficient for material work, per web requirements §4, which this component structurally enforces by requiring a `blocks` array on any message the co-founder produces via `runCofounderTurn`.

## 4. Business model view

`(app)/p/[projectId]/plan/page.tsx` renders all 17 section cards from `pack.listBusinessModelSections`, using the status vocabulary in `02-domain-model-delta.md` §4 (`draft, assumption_heavy, researching, needs_founder, supported, stale, blocked, accepted`) via a new `sectionStatusPresentation` entry in `packages/ui` (extending the existing `sectionStatusPresentation`/`artifactStatusPresentation` token maps, not inventing a new presentation system). The detail view (`plan/[section]/page.tsx`) reuses the existing diff-rendering logic already built for `pack.getDiff` in `PackSectionView`, generalized to any of the 17 keys.

## 5. Work board

New route `(app)/p/[projectId]/work/page.tsx`. Views map directly onto `job.list`'s `view` parameter (§1 table above) plus a founder-task lane. Kanban view uses `@dnd-kit/core` + `@dnd-kit/sortable` (decision D21): columns are the product-facing job states from `02-domain-model-delta.md` §2 (`proposed, queued, running, needs_founder, needs_approval, complete`, plus a `blocked` column); `onDragEnd` calls `job.updateSettings`/`job.retry`/`sprint.control`-backed mutations depending on the transition, with an optimistic update reconciled against the next `sprint_progress`/`job_state_changed` SSE event — this follows the same "TanStack Query + reconcile via SSE" pattern already used for sprint activity, not a new state-sync mechanism.

Job card fields (web requirements §6) map directly onto `AiJobSummary` (`04-backend-services-and-trpc-delta.md` §4) — no additional backend work needed here, only rendering. The advanced-settings panel is a form bound to `job.updateSettings`, reusing the existing `provider.listConnections` and budget summary queries so the founder's dropdown of allowed models/providers is never hand-maintained twice.

## 6. Founder task cards

New `components/work/founder-task-card.tsx`, rendered both inside the Work board and as its own focused view when opened. Fields match web requirements §7 exactly, all sourced from the `FounderTask` entity — no derived-on-the-fly text. "Help me" calls `founderTask.requestHelp`, which surfaces its result as a `ConversationMessage`, rendered by the same `ConversationMessageView` component used in the persistent panel (§3) — reused, not reimplemented for this one context.

## 7. Research review and scorecard experience

`(app)/p/[projectId]/research/page.tsx`'s "before starting" preview (web requirements §8) is the existing `sprint.preview` screen, extended to also render `SprintContract`'s new `whyNow`/source-category/geography/date-range fields (`02-domain-model-delta.md` §2) plus the "limitations" text the co-founder's decision output includes. The "after completion" view renders `ResearchFinding`s grouped by `affectedSectionKeys`, with conflict/agreement badges from `conflictsWithFindingIds`.

The scorecard experience (web requirements §9) is a new `components/score/scorecard.tsx`, rendering `score.getCurrent`/`score.getHistory`/`score.explain` — trend chart reuses whichever charting library is already pinned in `docs/plan/implementation/00-tech-stack-and-versions.md` (Visx or Recharts; do not add a second charting library).

## 8. Plan revision review

`pack.getDiff` already returns field-level before/after; extend its rendering (in the generalized `plan/[section]/page.tsx`) with: provenance badges (from the existing `Provenance` value object, no new type), citations inline (via `ResearchFinding.citationIds` → `citations` repo), score before/after (from `score.getForRevision`), "accept this section"/"accept all safe" buttons bound to the new `pack.acceptSection`/`pack.acceptAllSafeSections` procedures, and a warning banner driven by `acceptAllSafeSections`'s server-computed "unsafe" flag (never a client-side heuristic, since the safety rule — touches canonical price/unit/currency/cost — must be enforced the same way whichever client calls it).

## 9. Responsive and accessibility

No new pattern. Breakpoints (`sm`/`md`/`lg`/`xl`) and the "status must not rely on color alone" rule are already established in `docs/plan/implementation/02-web-frontend-architecture.md` and `@foundry/ui`'s `StatusPill` (which already pairs an icon/label with color) — every new component in this document reuses `StatusPill`, `Badge`, `ProgressBar`, `BudgetGauge` rather than introducing new visual primitives.

## 10. Removed/relocated, not orphaned

Per `00-README.md` rule 2: `lib/journey.ts` and `journey-stepper.tsx` lose their role as primary navigation chrome but are not deleted outright until their remaining use (phase label inside a section's "why" text, if kept at all) is confirmed in implementation — if no remaining call site exists once the Overview and Business model views ship, they are deleted in the same change, per the cleanup list in `09-migration-sequencing-and-cleanup.md` §3.
